# Рабочие доступы (team-vault)

[![Python 3.13](https://img.shields.io/badge/python-3.13-blue.svg)](https://www.python.org/)
[![Django 5.2 LTS](https://img.shields.io/badge/django-5.2%20LTS-green.svg)](https://www.djangoproject.com/)
[![PostgreSQL 18](https://img.shields.io/badge/postgresql-18-blue.svg)](https://www.postgresql.org/)
[![Docker Compose](https://img.shields.io/badge/docker--compose-ready-brightgreen.svg)](https://docs.docker.com/compose/)
[![Security: AES-256-GCM](https://img.shields.io/badge/crypto-AES--256--GCM-red.svg)](docs/decisions.md)

Корпоративное защищённое хранилище секретов и рабочих доступов команды, разработанное с нуля. Современная, удобная и безопасная замена **TeamPass** без устаревшего PHP/MySQL-стека.

Цель: сотрудники (включая нетехнических специалистов) могут безопасно хранить, использовать и передавать рабочие учётные записи. Пароли компании остаются в компании, а не в личных блокнотах уволившихся сотрудников.

---

## Архитектура и стек

- **Backend:** Python 3.13, Django 5.2 LTS, Gunicorn.
- **База данных:** PostgreSQL 18-alpine (runtime-пользователь изолирован, без прав `SUPERUSER`/`CREATEDB`).
- **Шифрование:** Envelope Encryption на базе библиотеки `cryptography` (AES-256-GCM с контекстной привязкой AAD по ID записи и версии, уникальный случайный DEK на каждое значение, главный ключ `VAULT_MASTER_KEY`).
- **2FA / TOTP:** Серверная генерация одноразовых кодов (`pyotp`) по явному нажатию с аудитом каждого запроса. QR и seed-секрет обычным пользователям не раскрываются.
- **Frontend:** Серверные Django Templates, чистый адаптивный CSS и Vanilla JS без тяжелых SPA-фреймворков. Автоматическая поддержка светлой/тёмной темы, выдвижная шторка на мобильных, серверный combobox-поиск (по 20 записей на страницу).
- **Интеграции:** 
  - Microsoft Entra ID (OIDC / PKCE через `Authlib`, привязка `tenant + oid`);
  - Active Directory / LDAPS (доменная авторизация через `ldap3` со строгой проверкой TLS-сертификатов);
  - Локальные учётные записи (логин и пароль) для работы без внешних провайдеров.

## Быстрый запуск

### Вариант 1: Запуск готового образа из GitHub Container Registry (GHCR)

Для развертывания на сервере без необходимости локальной сборки:

```bash
# 1. Скачайте compose.prod.yaml и переименуйте в compose.yaml
curl -fsSL https://raw.githubusercontent.com/Ttolyanich/team-vault/main/compose.prod.yaml -o compose.yaml

# 2. Инициализируйте файл окружения со случайными криптостойкими ключами и паролями:
python3 -c "$(curl -fsSL https://raw.githubusercontent.com/Ttolyanich/team-vault/main/scripts/init_env.py)"

# 3. Настройте адрес вашего сервера в .env:
# PUBLIC_URL=https://vault.company.local:8443
# ALLOWED_HOSTS=vault.company.local,10.15.26.204,localhost

# 4. Запустите сервисы:
docker compose pull
docker compose up -d
docker compose ps
```

### Вариант 2: Сборка из исходников

```bash
git clone https://github.com/Ttolyanich/team-vault.git /opt/team-vault
cd /opt/team-vault

python3 scripts/init_env.py
# Отредактируйте PUBLIC_URL и ALLOWED_HOSTS в .env под свой адрес
docker compose up -d --build
docker compose ps
```

`init_env.py` один раз создаёт `.env` со случайными паролями и ключами. Существующий `.env` он не перезаписывает. Права файла на Linux — `0600`.

По умолчанию приложение слушает `127.0.0.1:8081` (или заданный через `BIND_IP` и `APP_PORT`). Для доступа из сети рекомендуется HTTPS reverse proxy (пример конфигурации: `deploy/nginx.conf.example`).

## Аутентификация и пользователи

### 1. Локальные учётные записи (для работы без M365 и AD)
- **Создание:** Администратор может создавать локальных сотрудников прямо из веб-панели («Команда» → кнопка «＋ Сотрудник»): задаются логин, ФИО, почта, пароль (от 16 символов) и подразделение.
- **Вход:** На странице логина доступна стандартная форма входа по логину и паролю. Если внешние провайдеры (M365/AD) не настроены, форма активна по умолчанию.
- **Сброс пароля:** При необходимости администратор может установить новый пароль сотруднику в его карточке. При этом старые сессии пользователя мгновенно инвалидируются (`auth_revision`).

### 2. Резервный локальный администратор
- Логин задаётся `LOCAL_ADMIN_USERNAME`, пароль — `LOCAL_ADMIN_PASSWORD` в `.env`. В базе хранится только хэш.
- Для смены пароля измените `LOCAL_ADMIN_PASSWORD` в `.env` и пересоздайте контейнер:
  ```bash
  docker compose up -d --force-recreate app
  ```

### 3. Microsoft 365 (Entra ID)
- Настройка в веб-панели («Интеграции → Microsoft 365»).
- Поддерживает OIDC Discovery, PKCE, проверку `tenant` и `oid`.
- Redirect URI для регистрации в Entra: `https://<ВАШ-АДРЕС>/auth/microsoft/callback/`.
- Секрет приложения хранится в БД в зашифрованном виде.

### 4. Active Directory (LDAP / LDAPS)
- Настройка в «Интеграции → AD / LDAP».
- Поддержка LDAPS и StartTLS со строгой проверкой доверенной цепочки сертификатов CA.
- Привязка учетной записи по неизменяемому `objectGUID`. Пароли сотрудников в БД не сохраняются.

## Модель доступа и безопасность

### Иерархия подразделений и динамический ответственный
- У сотрудника **одно основное подразделение**, у подразделения — **один руководитель**.
- Резервные коды 2FA видит **только текущий руководитель**: для общего хранилища — руководитель подразделения, для личного — руководитель сотрудника.
- При переводе сотрудника или смене руководителя доступ к резервным кодам **автоматически переходит новому руководителю**. Уволенный или сменивший должность руководитель мгновенно теряет доступ.
- Административная роль сама по себе не раскрывает чужие резервные коды 2FA.

### Разделение рабочего и административного контекста
- Вкладка «Мои рабочие секреты» администратора содержит **только его личные пароли**, а «Общие хранилища» — только доступные его отделу.
- Глобальный поиск по чужим записям вынесен в отдельный административный блок «Секреты сотрудников» и сопровождается обязательной фиксацией в аудите.

### Корзина и мягкое удаление
- Секреты и общие хранилища удаляются только мягко (без окончательной очистки).
- Доступ к просмотру корзины и восстановлению имеют только администраторы приложения.

## Резервное копирование и сохранность данных

> [!IMPORTANT]
> **Ответственность за сохранность данных и организацию бэкапов:**
> Приложение обеспечивает криптографическую защиту данных и разграничение доступа, но **за регулярное резервное копирование и сохранность данных отвечает системный администратор**. 
> Потеря доступа к серверу или случайное удаление тома БД без регулярных бэкапов приведет к безвозвратной утрате секретов.
> 
> - **Внешняя СУБД (Enterprise):** Вы можете использовать любую существующую промышленную инсталляцию PostgreSQL (Managed PostgreSQL в облаке, внешний кластер с репликацией, Patroni, pgBackRest или WAL-G), просто указав строку подключения `DATABASE_URL` в `.env`. В этом случае сервис `db` в `compose.yaml` можно отключить.
> - **Скрипты бэкапа:** При использовании встроенного PostgreSQL контейнера настройте регулярное снятие дампов (через cron или планировщик задач) с обязательной выгрузкой на независимый изолированный сервер, сетевое хранилище (NFS/SMB) или S3-совместимое объектное хранилище.
> - **Сохранность мастер-ключа:** Обязательно сохраните резервную копию конфигурационного файла `.env` (в первую очередь параметров `VAULT_MASTER_KEY` и `SECRET_KEY`) в надёжном защищённом корпоративном хранилище. **Без `VAULT_MASTER_KEY` восстановить зашифрованные секреты из любого дампа базы данных математически невозможно.** Никогда не запускайте `docker compose down -v` на рабочем стенде!

На сервере доступны готовые утилиты автоматического бэкапа и проверочного восстановления:

```bash
cd /opt/team-vault

# Создать зашифрованный MVCC-дамп базы с контрольными суммами таблиц:
sudo python3 scripts/backup.py

# Проверить восстановимость копии в отдельном временном изолированном Docker-контейнере:
sudo python3 scripts/restore_check.py backups/backup-ДАТА-ID.json

# Периодическая очистка устаревших технических сессий и кешей:
sudo docker compose exec app python manage.py cleanup_technical
```

Скрипт `restore_check.py` разворачивает дамп в изолированную тестовую базу, проверяет контрольные суммы всех таблиц, расшифровывает тестовые секреты и проверяет работу TOTP, после чего бесследно удаляет тестовый клон.
